# 0001 - 分组重建不等待用量刷新

2026-09-15 事故：4 个组全部进入终态后，唯一的恢复路径（重建分组）被「全量 `/usage` 刷新必须全部成功」绑架——`RefreshAll` 串行跑在请求路径上、使用请求的 context，而 `/usage` 从该主机经常 20 秒超时（10 个 Key 一次全量最坏 200 秒），客户端先断开就把刷新取消。结果：池内 10 把 Key 全部可用、剩余约 4,100 额度，服务却持续 20 分钟返回「没有可用 Key」。决定：重建立即用池内已知的容量进行；刷新转后台、脱离请求 context、尽力而为。

## Considered Options

- 重建前要求刷新成功（原实现）：一次慢 `/usage` 即全池不可用。
- 重建后异步补刷，接受数据陈旧度上界一个周期（采纳）：分组均衡本来就是启发式，可用性优先。

## Consequences

- 重建时的分组均衡可能基于陈旧数据；随后的补刷让下一个周期收敛。
- 补刷入口本身需要节流（见 ADR-0002），否则重建风暴会连发 `/usage`。
