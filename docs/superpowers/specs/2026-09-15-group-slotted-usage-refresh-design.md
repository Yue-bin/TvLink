# 按组错峰的用量刷新设计

## 目标

把 `/usage` 刷新的时间形状从「每小时一次、10 个 Key 在 14 秒内连发」改为「组为槽、组间错开、组内微抖动」，并让三个刷新入口共用按 Key 的刷新节流与 429 退避。每周期每 Key 一次的总量不变，改变的只是时间分布；同时把刷新行为变成可观测的指标。

## 背景

- Tavily 对 `/usage` 有独立限流（官方口径 10 次/10 分钟，dev/prod 相同；实测按 Key 生效，当前部署一把 Key 一个账号）。
- TvLink 有三个入口会打 `/usage`：定时刷新、分组重建后的后台补刷、Research 结算时的单 Key 刷新。
- 组的存在理由是控制 Key 使用节奏（见 `CONTEXT.md`）；刷新的时间形态属于同一关注点。

## 调度

- 周期 = `usage_refresh_interval`（保持 1h，不新增配置项）。
- 分组启用时：周期按组数均分为槽，第 i 槽 = 轮换顺序中的第 i 组，槽内刷新该组全部 Key。槽边界加 ±10%（槽间距）随机偏移，槽内每 Key 加 0–10s 随机偏移。
- 未启用分组时：Key 按配置顺序均匀铺进周期。
- 重建分组会重排槽位：新槽期望时刻 = 重建时刻 + 新槽位偏移，但不得早于该 Key 的节流下限。因此重建后相位随成员变化，Key 数据陈旧度上界约为一个周期。

## 刷新节流

每次 `/usage` 尝试后更新该 Key 的「下次可刷新时刻」：

- 成功 → 本次时刻 + 周期 + [0,10s) 抖动；
- 失败（非 429）→ 本次时刻 + 2 分钟（安静重试，约 5 次/10 分钟）；
- 429 → 本次时刻 + max(Retry-After, 300s)。

三个入口统一遵守；到期集合之外的 Key 不发请求。启动时的全量刷新是唯一例外，并作为各 Key 节流的起点。重建后的后台补刷因此退化为「补刷冷却已到期的 Key」：重建风暴时第一次补刷后其余 Key 自动进入节流，不会反复连发；Research 结算遇到节流则把对账顺延到下一个槽。

## 观测

- 状态条显示最近一批刷新的结果（批内 Key 数、失败数、错误原文）。
- 新增三条指标：近一个周期的 `/usage` 请求总数、任意 60 秒滑动窗口内的最大请求数（最大连发）、近 10 分钟的 429 计数。
- 监控页每 Key 的「实际更新」保持不变。

## 验收

1. 近一个周期 `/usage` 请求总数 ≈ Key 数（每 Key 每周期一次，重试除外）；
2. 任意 60 秒窗口内最大请求数 ≤ 组内 Key 数（典型 2–3）；
3. 近 10 分钟 429 计数为 0；出现 429 时按退避下降而非重复撞击。

## 测试覆盖

槽位与抖动边界；重建后的重排与节流下限；未分组回退；到期集合与等待时长计算；三种退避；三个入口的节流遵守；指标窗口计算；监控渲染。
